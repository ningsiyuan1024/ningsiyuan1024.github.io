正文

如果你要给一个代理开放你所有的邮箱、Slack、Notion 和 Google Drive，你会怎么做？

1. 把一切都嵌入到向量数据库里，在运行时检索相关片段。
2. 给代理提供直接访问各个数据源的工具，让它自己穿行其中，按需拉取信息。

从搜索到导航

当你把 Claude Code 指向一个代码库时，它做的不是简单搜索，而是导航。

它会阅读目录结构，沿着 import 关系往下走，检查依赖，逐步建立一张文件与模块分布图。它探索得越多，结果通常越准确。

如果把这种模式应用到个人数据和工作数据中，再加上一层学习闭环，让代理在使用中不断改进，就会得到我所说的 context agent，也就是上下文代理。

编码代理导航的是代码库。

上下文代理导航的是别的一切：你的邮件、日历、文档、数据库、Slack 线程。

关键在于，每一个数据源都通过自己的原生接口来查询：

  • 邮件按发件人和日期查询
  • 数据库用 SQL 查询
  • 日历按时间范围查询
  • 文件系统按结构导航

这里没有任何东西需要先被压平成向量。

三代上下文获取方式

一个代理的回答质量，取决于它能拿到什么样的上下文。

这个问题重要到足以成为一门独立学科：Context Engineering，上下文工程。

整个行业已经经历了三代上下文获取方式，每一代都解决了当时最迫切的问题。

第一代：Semantic RAG（2023）

做法是这样的：

把文档嵌入，存进向量数据库，在查询时进行检索，再把最相关的结果注入到提示词里。

RAG 让大模型无需把所有知识都塞进上下文窗口，也能访问大型知识库。这是一次真正的突破，也带来了惊人的开发者采用率。围绕它甚至诞生了整批公司。

但它有两个明显限制：

1. 搜索查询本质上就是用户的原始输入

系统把用户输入嵌入后，去找语义最接近的内容，但并不会先推理到底需要哪些信息，再去搜索。

2. 向量存储把一切压平为同一种接口

你的文档、邮箱、日历，最后都被切块、嵌入、统一检索。不同数据源原本的结构与查询语义，被抹平了。

第二代：Agentic RAG（2024–2025）

随着 tool calling 的能力变强，Agentic RAG 开始兴起：模型通过工具调用来搜索知识库。

在我看来，工具调用能力的提升，一直是模型能力进化里最被低估的一环。

这一代最关键的变化是：

上下文搜索从 query time，也就是基于用户输入立即检索，变成了 run time，也就是在执行过程中按需检索。

代理不再只是把用户原始输入丢进向量检索，然后赌能不能找到对的片段；它会先推理自己真正需要什么信息，再发起更有针对性的搜索。

这解决了第一代的第一个问题。

但第二个问题依然存在。

代理依旧是在搜索一个向量库，只是变得更聪明了，知道该何时搜索、搜索什么。各个数据源依旧是被压平的，也依旧没有关于上一次什么方法有效的记忆。

第三代：Agentic Navigation（2026–）

这就是上下文代理。

代理不再搜索向量库，而是导航一张 context graph，也就是上下文图谱：由多种异构数据源组成，每个数据源都按自己的方式被访问。

它会建立一张信息分布地图，学习哪些检索策略更有效，并在每一次交互中持续改进。

从第二代到第三代的真正跃迁，是把 navigation over search，也就是导航优先于搜索，变成上下文获取的核心原语。

一个 SQL 数据库，就应该用 SQL 查询。

一个日历，就应该按时间范围查询。

一个文件系统，就应该沿着结构去导航。

上下文代理在实践中是什么样

Pal 是一个个人上下文代理，它会学习你的工作方式。

它会在一组异构数据源之间导航，来为任务收集上下文：

1. 本地文件系统：存放偏好、语气指南和模板
2. Gmail、Google Calendar、Slack 这样的工具
3. PostgreSQL 数据库：存放结构化数据，比如笔记、人物、项目、决策

每个数据源都保留自己的原生查询接口：

  • 数据库用 SQL
  • 邮件按发件人筛选
  • 文件按目录结构导航

再加上一层学习闭环，每次交互都会让下一次做得更好。

上下文代理与普通代理真正不同的地方，在于它的执行循环是为路由与导航设计的：

1. 根据输入消息识别意图
2. 从 knowledge 和 learnings 中召回元数据与路由模式
3. 按 learnings 指导的顺序，从正确的数据源读取信息
4. 通过工具调用执行动作
5. 把这次经验沉淀下来，让下一次更好

导航循环是怎么工作的

假设你对 Pal 说：

准备我和 Sarah 的会议材料。

Pal 会这样工作：

1. 识别任务类型

它先把任务分类为 meeting prep，也就是会议准备。

2. 召回已有知识与经验

它从 knowledge 中知道，Sarah 是一个联系人，关联着某个项目，还有一个名为 partnership-brief.md 的文件。

它又从 learnings 中知道，这类任务有一条已经验证过的路由策略：

日历 → 邮件 → 笔记 → 文件

3. 从正确的数据源按顺序读取

于是它会：

  • 通过 CalendarTools 读取会议与议程
  • 通过 GmailTools 读取 Sarah 昨天发来的邮件线程
  • 通过 SQLTools 读取被标记为 sarah 的笔记
  • 通过 FileTools 读取项目简报

4. 执行动作

它把这些内容整合成一份连贯的 briefing：

  • 这是会议议程
  • 这是 Sarah 昨天发来的信息
  • 这是项目当前状态
  • 这是你笔记里尚未解决的问题

5. 学习

它会记录一个新发现：

与 Sarah 相关的上下文通常横跨这四个数据源。

所以下一次再遇到 Sarah 相关任务时，它就不会从大范围搜索开始，而会直接去这四个地方。

四个数据源。

每个都通过原生接口访问。

每个都先独立总结，再统一综合。

Knowledge 与 Learnings

真正的改进发生在第 2 步和第 5 步。

它们由两个边界仍然有些模糊的系统共同驱动：Knowledge 和 Learnings。

Knowledge：地图

Knowledge 是地图。它是一个关于信息分布位置的元数据索引。

随着 Pal 工作，它会记录：

  • 有哪些文件存在
  • 建了哪些表
  • 可用的数据源有哪些
  • 某类信息以前是从哪里找到的

Knowledge 记录的是结构性认知，不是内容本身。

举个例子：

如果 Pal 发现 Project X 的相关信息分散在一张 SQL 表、一个 markdown 简报和一个 Gmail 线程里，它就会把这组映射保存成一个 discovery。

下一次有人问到 Project X，它就会直接导航到这三个位置。

Knowledge 的条目会按类型加前缀：

  • File：有哪些上下文文件，它们的用途和意图标签是什么
  • Schema：有哪些 SQL 表，它们的结构是什么
  • Source：有哪些工具可用，它们分别能做什么
  • Discovery：某个主题的信息过去是在哪些地方找到的

在多用户环境下，Knowledge 是共享的。

信息分布地图对所有人都一样。

Learnings：罗盘

Learnings 是罗盘。

随着 Pal 完成任务，它会记录：

  • 哪些检索策略成功了
  • 它观察到你有哪些工作模式
  • 你曾经做过哪些纠正

比如它发现，会议准备最有效的顺序是：

先看日历，再看邮件，再看笔记，最后看文件。

那它就会把这条顺序保存下来。

再比如你纠正它说：

Sarah 在 Acme Corp，不在 Acme Inc。

这个纠正会拥有最高优先级，始终压过其他信息。

Learnings 同样有类型前缀：

  • Retrieval：某类请求中，哪些数据源与查询方式最有效
  • Pattern：代理观察到的重复行为模式
  • Correction：用户明确给出的修正，这类信息永远优先

Knowledge 和 Learnings 的区别在于：

  • Knowledge 记录信息在哪里
  • Learnings 记录应该怎么到达那里

Knowledge 是跨用户共享的，因为文件系统、数据库结构和工具能力是客观事实。

Learnings 则按用户命名空间隔离，因为你的检索偏好、你的修正、你的工作习惯，应该只属于你。

在这两种系统里，提示词本身都没有变。

真正变强的，是代理带到提示词里的上下文质量。

定时任务

一个只在你发出请求时才运行的上下文代理，本质上还是被动的。

定时任务让它变得主动。

Pal 默认提供五类定时任务：

  • 每日简报：工作日早上 8 点

汇总日历、邮件和优先事项

  • 收件箱摘要：工作日中午 12 点

总结上午邮件，并标出需要回复的内容

  • 每周回顾：周五下午 5 点

自动填写 weekly-review 模板，并保存到 meetings/ 目录

  • 上下文刷新：每天早上 8 点

重新索引上下文文件，并清理过时事实

  • 学习摘要：周一上午 10 点

总结近期 learnings 中出现的模式

这些任务的结果在需要时还可以发送到 Slack。

接下来会怎样

Pal 是一个开源实验。

它已经能工作，但仍然是一个实验。

上下文代理同样可以为团队和组织构建：

一个能在 Slack、Notion、Drive 和内部数据库之间导航的代理；

一个会学习哪些检索策略最适合你们组织数据的代理；

一个随着使用不断变强的代理。

如果你试用了 Pal 并发现哪里坏了，欢迎通过提 issue 的方式反馈。

基于它继续构建，拆解它，改造它，让它真正成为你的系统。
