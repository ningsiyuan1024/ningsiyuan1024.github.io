这篇文章讲的是如何构建你自己的智能体（agentic software engineering），而不是如何使用现成的编码智能体（coding agents）。

到现在你大概率已经用过一些智能体，或者至少听说过 Claude Code、Codex 或 OpenClaw。你有没有想过：要自己做一个智能体，到底需要什么？

很多人把智能体理解成「提示词 + 工具调用的循环」。这个理解不算错，但它不是生产级架构。

当你的智能体需要知道自己在和谁说话、需要维护状态、要处理并发请求、要执行敏感操作、还要在工具调用失败时继续活下去……它就不再是“LLM + 工具”，而是一个分布式系统。

做出一个能跑的智能体很容易。市面上有 75 个框架能帮你做到。

难的是运行时（runtime）：那层包在智能体外面的“支架/框架（harness）”，让它在真实世界里可靠地工作。

这就是 智能体软件工程（agentic software engineering） 的核心。

Build. Serve. Connect.

这是我对“交付智能体软件”的思维框架：

1. Build the agent（构建智能体）

定义模型、工具、知识库、记忆、存储和护栏（guardrails）。这是大多数框架能提供的那一层。

2. Serve it as an API（以 API 形式提供服务）

按用户隔离（user-scoped）、按会话隔离（session-scoped）、支持水平扩展（horizontally scalable）。加上持久化存储、流式输出、后台执行、重试语义（retry semantics）。

这是多数智能体产品卡住的地方。不是因为智能体“不好用”，而是因为它没有围绕自己建立起可规模化、可可靠运行的基础设施。

3. Connect it to where users live（接入用户所在的场景）

你的产品、Slack、Discord、MCP……任何用户真实工作的地方。

在 notebook 里的智能体是实验；在用户所在场景里的智能体才是产品。

智能体软件的 6 大支柱（The 6 Pillars of Agentic Software）

做智能体是 AI 工程；把它跑在生产环境里是软件工程。两者结合，才构成 智能体软件工程（agentic software engineering）：把智能体作为生产级服务来构建、运行与扩展的实践。

支撑它的六根柱子是：

1. Durability（耐久性 / 可恢复性）

智能体会跨多个步骤推理，会调用可能超时的工具，也可能半途失败。

如果你的智能体在 15 步中的第 12 步崩了，重启可能会重复产生副作用（side effect），或者丢掉关键上下文。

智能体软件需要能暂停、恢复、做 checkpoint、并优雅地故障恢复。

耐久性把失败变成“从中断处继续”，而不是“从头再来”。

2. Isolation（隔离）

智能体软件会同时服务成千上万用户。每个用户都需要自己的 session、自己的记忆、自己的上下文。

请求里带个 user_id 很简单；难的是把智能体触达的每一种资源都隔离到位。

数据库、向量库、模型提供商……都必须严格遵守用户边界。一个漏掉的过滤条件，就可能变成数据泄露。

3. Governance（治理 / 权限治理）

能行动的智能体也能造成破坏。查一条记录没问题；删记录或退款就需要审批。

智能体软件需要分层授权：哪些可以自动执行，哪些需要用户批准，哪些需要管理员签字。

今天多数智能体都是“默认自动执行、几乎无监督”。但随着能力提升，治理会变成产品本身。

4. Persistence（持久化）

没有持久化存储的智能体无法学习、无法积累上下文、无法变好。

我们需要把 session、记忆、知识存进数据库。持久化状态是把 chatbot 变成产品的关键：每一次对话都能让下一次更好。

5. Scale（规模 / 可扩展性）

一千个用户同时打你的智能体：请求排队、触发模型限流、工具调用争抢资源。

传统服务主要调用自家后端；智能体软件要调用外部模型 API 和第三方工具——你会继承它们的限流、延迟和宕机。

扩展智能体软件，本质是在你无法控制的依赖周围做扩展。

6. Composability（可组合性）

当智能体是一个服务，别的智能体可以调用它；你的前端可以调用它；你的 Slack bot 可以调用它；MCP 客户端可以发现它。

它会变成架构里的“积木块”，每一个新集成都只是一次标准 API 调用。

这就是单智能体工具如何进化成多智能体系统。

这些都不新鲜。几十年来我们一直在构建可靠的分布式系统。只是 AI 行业还没把这些经验带过来，所以每一次失败的部署里，你都能感受到它的缺位。

从理论到实践（From Theory to Practice）

照例，我带来了代码。下面是你今天就能开始搭建自己的智能体服务的方法。

# 1. Clone the repo
git clone \
    https://github.com/agno-agi/agentos-docker-template.git \
    agentos

cd agentos

# 2. Set your model provider key
cp example.env .env
# Edit .env and add OPENAI_API_KEY

# 3. Start the application
docker compose up -d --build

# 4. Load documents for the knowledge agent
docker exec -it agentos-api python -m agents.knowledge_agent

这会给你一个容器化服务，包含：

  • 持久化存储（Postgres）
  • 两个起步智能体：
  • 一个知识智能体（使用 Agentic RAG）
  • 一个 MCP 智能体（用于外部工具调用）
  • 一个你可以从任何地方连接的 REST API

我用 Docker 做这个模板，因为 Docker “到处能跑”：你的笔记本、AWS、GCP、Azure、Railway。你本地开发的容器，就是你上线到生产环境的容器。README 覆盖了上手需要的一切。

服务跑起来后：

1. 打开 http://localhost:8000/docs 查看你的 API。
2. 在 os.agno.com 连接 Web UI：你可以和智能体聊天、追踪运行轨迹（trace runs）、管理知识库、创建定时任务、审批敏感工具调用。——一个 UI 管理整套智能体软件。

新增一个你自己的智能体，只需要几行 Python 和一次重启。换模型只要改一行。还能从 100+ 集成里加工具。这个模板只是起点；想深入了解请阅读 Agno 文档。

治理与追问（Governance & Elicitation）

大多数智能体在工具调用上几乎没有监督或可审计性。但在真实世界里，我们需要分层授权：

1. 可以自由运行的工具
2. 需要用户批准的工具
3. 需要管理员批准的工具

智能体还需要会问问题（经常被称为 elicitation）。Claude Code 团队分享过一篇很棒的文章，讲 Claude 的 AskUserQuestion 工具。

在 Agno 里，这对应 UserFeedbackTools。下面是一个客服智能体示例：它可以自由查询订单；当信息不足时，用结构化问题向客户追问；在发起退款前会等待用户批准：

support = Agent(
    id="support",
    name="Support",
    model=OpenAIResponses(id="gpt-5.2"),
    db=agent_db,
    tools=[
        lookup_order,             # 自动执行
        search_help_docs,         # 自动执行
        issue_refund,             # 需要用户确认
        UserFeedbackTools(),      # 结构化提问
    ],
    instructions=instructions,
    enable_agentic_memory=True,
)

当客户要求退款时会发生什么？

  • 智能体会先自己查询订单，不需要权限。
  • 然后它遇到一个决策点：客户为什么要退款？
  • 它不会猜，而是给出一个结构化问题，提供清晰选项：有瑕疵、发错货、不想要了。
  • 客户选一个。接着智能体准备调用退款工具，但因为退款有真实后果，它会暂停等待用户批准。
  • 用户批准后，智能体才会执行退款工具。

一次对话里包含三层“代理性（agency）”。你可以在这里查看完整代码（原文如此）。

智能体知道什么时候该行动、什么时候该追问、什么时候该等待。这就是治理在实践中的样子。运行时必须支持这三种模式，并且它们之间的切换要自然。

注：UI 里的审批流程还在积极开发中。退款应该等待管理员批准，而不是用户批准。SDK 已实现，但 UI 还没做完；这周会修复。

智能体是分布式系统（Agents are distributed systems）

“5 个等级（The 5 Levels）”描述了智能体软件如何随着能力提升而变得更复杂；“7 宗罪（The 7 Sins）”描述它们如何在生产环境里失败；“6 大支柱（The 6 Pillars）”描述如何把它们正确构建起来。

这三套框架反复强调的是同一个结论：智能体软件工程是一门学科。

越早内化这一点的团队，越能做出优秀的产品；还把智能体当脚本在写的团队，会持续偏离用户真正需要的东西。
