==============================================

做 AI Agent 落地的初阶、中阶产品经理，大概率都踩过评测的坑：上线前随便测几句对话，上线后数据崩盘却找不到根因，迭代全靠改 prompt 碰运气。最后既拿不到业务结果，也扛不住合规风险。

这套框架的目标，不是把评测做成“对话好不好看”的主观判断，而是把它变成一套可量化、可复制、可追溯、能真正驱动业务迭代的方法。完整流程共 8 步，本文合并为一篇，方便直接收藏和复用。

Step 1：定义业务目标

评测的核心是服务业务，而不是评判对话本身。所有评测动作开始前，都必须先锚定 3 个不可动摇的核心基准，后续所有环节都要围绕这三点展开。

1）核心业务目标
绑定可量化的业务结果，而不是技术指标。
以电商商家客服 Agent 为例，核心目标通常是：响应率、售前咨询转化率、客户满意度。评测设计必须服务这些结果，不做与业务无关的冗余动作。

2）用户目标动作
明确用户从触达到转化的完整路径。
例如：售前咨询 → 消除疑虑 → 转化。
这条链路上的每一个节点，后续都要能映射到对应的评测维度和指标。

3）护栏指标
这是不可突破的业务底线。
例如：错误承诺、违规话术、用户投诉。业务效果再好，只要护栏指标被击穿，整个版本都应视为失败。

实战避坑：不要把技术指标当业务目标。幻觉率低，不代表转化率就高；响应更快，也不代表用户更愿意下单。评测的起点，必须是业务真正能拿到的结果。

Step 2：拆任务树

很多团队评测无标准、全凭主观判断，核心原因不是模型不够强，而是没有做任务拆解。

像“用户咨询商品”这种泛场景，根本无法实现精准评测，必须继续往下拆，直到最小可量化单元。固定拆解逻辑建议统一为：

场景 → 意图 → 任务 → 任务成功定义

例如：

  • 场景：商品售前咨询
  • 用户意图：确认服装是否支持机洗
  • 核心任务：准确告知用户商品洗护规则，打消购买顾虑
  • 任务成功定义：正确引用商品详情页中的洗护说明；无事实错误；用户没有围绕同一主题继续追问

只有拆解到“单个任务 + 明确成功标准”，你的评测才能从“主观感觉答得还行”，转化为“这个任务是否完成”的标准化动作。地基不牢，后面的指标、样本、打分、线上监控，都会失效。

Step 3：搭建评测指标体系

很多 PM 做指标时，要么只盯一个最终转化率，要么零散堆十几个技术指标，结果一旦数据波动，根本找不到是哪一环出了问题。

一套真正能驱动迭代的评测指标体系，必须分成 3 层，缺一不可。

1）北极星业务指标

这是最终结果指标，直接与业务目标强绑定，是版本迭代的验收标准。建议控制在 2～3 个即可。

常见例子：

  • 转化率
  • 订单 GMV / 订单量
  • 自助咨询解决率

要注意：北极星指标只回答“结果好不好”，不负责回答“问题出在哪”。

2）诊断指标

这一层才是定位问题的核心抓手。业务数据一旦波动，绝大多数根因都能在这里找到。建议至少覆盖 3 类：

回答质量类

  • 事实一致性
  • 幻觉率
  • 完整性
  • 可执行性
  • 多轮一致性

例如：转化率下滑，先排查是不是幻觉率上升，AI 输出了错误信息。

工具 / 检索链路类

  • 工具调用成功率
  • 检索命中率
  • 引用覆盖率

实战中，很多 Agent 翻车并不是模型本身，而是检索或工具链路先失效了，用户问题没有召回正确的业务信息。

交互体验类

  • 首轮解决率
  • 追问率
  • 重试率
  • 延迟
  • 转人工率

例如：转人工率上涨，可能不是回答错误，而是首轮解决率下滑、AI 无效追问过多，消耗了用户耐心。

3）护栏指标

这是不可突破的业务底线，要求是：版本迭代只能优化，不能退化，本质上就是“不变差”。

常见例子：

  • 合规拦截率
  • 投诉率
  • 违规内容出现率
  • 高风险话术漏拦截率

建议为每个指标设置明确阈值，例如：

  • 幻觉率 < 1%
  • 违规内容出现率 = 0
  • 高风险话术漏拦截率 ≤ X%
  • 工具调用成功率 > 98%

实战避坑：永远不要被整体数据蒙蔽。真实业务里，完全可能出现“整体转化率上涨 0.8%，但高风险售后场景投诉率上涨 270%”的情况。由于高风险场景用户占比低，问题不会立刻体现在整体大盘上，但后续一定会演变成大规模客诉。所以，护栏指标必须单独监控，哪怕样本量很小。

Step 4：构建场景样本集

实战中，评测结果和线上表现脱节，根源往往不在模型，而在样本失真。一套能真实反映线上表现的样本集，至少要抓住 3 个核心。

1）来源

优先采用真实线上 query，因为这最贴近真实业务场景。除此之外，再补充业务 FAQ、历史规则覆盖的高频问题，以及高风险特殊场景，例如退款、保价、售后维权等。

2）覆盖维度

样本集必须覆盖：

  • 任务类型
  • 难度梯度
  • 风险等级
  • 是否多轮

如果你的业务风险较高，建议高风险场景样本占比不低于 30%，避免“评测全优、上线翻车”。

3）字段设计

每条样本建议至少包含：

  • 用户 query / 上下文
  • 目标任务
  • 任务成功定义 / 关键检查点（来自任务树）
  • 必要事实源
  • 参考答案
  • 打分 rubric

提醒：不要用自己编造的虚假 query 搭建样本集。脱离真实用户表达方式的样本，评测结果几乎没有业务价值。

Step 5：设计打分 Rubric

很多团队多人评测同一条对话，最后打分结果不一致，核心原因不是大家理解不同，而是没有统一、可量化的打分标尺。

建议每个任务固定 6 个打分维度，并且每个维度都明确：

  • Pass / Fail 条件
  • 典型正例 / 反例
  • 是否属于一票否决项

建议的 6 个维度如下：

1）正确性
是否存在事实错误、幻觉。只要超出给定事实源、或者与事实源冲突，直接 Fail。

2）相关性
是否答非所问，是否偏离用户核心需求。

3）完整性
是否覆盖核心信息，是否遗漏关键内容。

4）可执行性
答案或建议是否可以直接落地，是否具有明确业务价值。

5）一致性
多轮对话中是否前后矛盾，是否遗忘上文关键事实。

6）合规安全
是否存在违规话术、错误承诺、敏感内容。出现即一票否决。

只有具备贴合业务的样本集和统一标准的打分规则，评测才能从“主观感受”升级为“可量化、可复制、可追溯”的专业动作。

Step 6：离线评测

离线评测是上线前的最后一道防火墙，目标很明确：把大部分问题拦截在上线前。

建议 3 种方式组合使用，兼顾覆盖度、准确率和成本效率。

1）自动评测

适合纯客观指标，通过脚本批量执行，例如：

  • 工具调用成功率
  • 检索命中率
  • 对话延迟

作用是快速筛掉低级问题，提升整体效率。

2）人工评测

主观项和高风险项必须由人工完成，例如：

  • 合规安全性
  • 多轮对话一致性
  • 回答可执行性

这部分不能简单交给 AI 替代，因为它承担的是上线前最关键的底线把控。

3）LLM Judge

可以用于扩大评测覆盖范围、降低人工成本，但前提是必须先用人工标注完成的黄金样本集，对 LLM 打分与人工打分的一致性进行校准。

只有当一致性达到可接受水平（例如 85%+，且高风险场景阈值更高）时，LLM Judge 才适合大规模使用。否则，评测结果没有参考价值。

落地建议：流程上可以先用自动评测筛掉明显不合格样本，再做人工评测和 LLM Judge，这样可以显著减少无效工作量。

Step 7：线上评测

常见误区是：只看整体转化率，数据涨了就觉得达标，数据跌了就完全无从下手。

正确做法是，线上评测必须拆成至少 4 层来监控，不仅看整体，更要按场景、任务、风险分层监控。

1）触达层

看有多少相关场景的用户 query 被 AI 正确承接。重点关注：

  • 该承接的没有承接
  • 不该承接的却乱承接

2）过程层

看中间链路是否健康，例如：

  • 回答率
  • 追答率
  • 点击率
  • 延迟
  • 转人工率

过程失效，结果一定受影响。

3）结果层

看真正的业务结果，例如：

  • 加购率
  • 下单率
  • 订单 GMV
  • 咨询解决率

注意，核心业务指标一定要按场景拆开看，否则很难定位问题究竟出在哪个任务环节。

4）负向层

重点监控负向业务结果和风险项，例如：

  • 投诉
  • 退款
  • 差评
  • 违规内容
  • 误导承诺
  • 敏感内容

这类隐藏风险必须单独监控，哪怕样本量极小，也要重点跟进。

实战避坑：永远不要被整体数据蒙蔽。哪怕整体大盘达标，也必须继续下钻到细分场景，否则高风险场景的问题很容易被整体数据掩盖，最终演变成大规模客诉或合规问题。

Step 8：做归因闭环，让评测真正驱动迭代

很多团队做完评测就结束了，最终评测只是“报表”，没有变成“能力”。真正有效的评测体系，最后一定要能形成归因闭环。

一个完整的闭环通常应该是：

指标波动 → 定位到场景 → 下钻到任务 → 对照样本与 rubric 复盘 → 找到根因 → 制定优化动作 → 回归评测 → 再上线验证

这里的根因，通常会落在几个固定位置：

  • 任务定义不清
  • 样本覆盖失真
  • prompt 策略失效
  • 检索召回异常
  • 工具调用链路故障
  • 高风险场景护栏缺失
  • 线上分流 / 承接策略异常

只有把评测、诊断、优化、回归串成闭环，评测体系才不是“做过了”，而是真正开始持续产生业务价值。

最后总结：8 步框架一图看清

  1. 定义业务目标
  2. 拆任务树
  3. 搭建三层指标体系
  4. 构建场景样本集
  5. 设计标准化打分 Rubric
  6. 做离线评测
  7. 做线上评测
  8. 建立归因闭环

核心结论

AI Agent 评测的本质，不是“测模型回答像不像人”，而是“测这套系统能不能稳定服务业务结果”。

所以真正有效的评测体系，必须满足 4 个要求：

  • 从业务目标出发
    ，而不是从技术指标出发
  • 拆到最小任务单元
    ，而不是泛泛评测“大场景”
  • 指标分层设计
    ，既能看结果，也能找根因
  • 同时盯住效果和风险
    ，避免被整体数据误导

如果你的团队现在做评测，还是停留在“上线前随便测几句、上线后看大盘、迭代靠改 prompt 碰运气”，那问题不在模型，而在于没有一套真正可执行的评测框架。

这 8 步，就是把 AI Agent 评测从“经验活”变成“工程化能力”的起点。
