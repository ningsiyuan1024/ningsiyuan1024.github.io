今天分享的文章是Self-Harness: Harnesses That Improve Themselves

https://arxiv.org/abs/2606.09498

什么是 Self-Harness？

现代 LLM Agent 的行为，不只由模型权重决定，也由它周围的 Harness 决定。

这里的 Harness，是模型与环境之间的执行层：它可能包括系统提示、可用工具、记忆和状态管理、验证规则、权限策略、运行时机制，以及失败后的恢复流程。

不同模型有不同的工具使用习惯、错误模式和提示敏感性。因此，同一个 Harness 放在不同模型上，效果可能完全不同；一个适合某个模型的 Harness，也可能不适合另一个模型。

但目前大多数 Harness 仍由人类专家设计。新模型快速出现以后，每次都依靠人工重新诊断、重新调整，这套方式很难扩展。

Self-Harness 想解决的问题是：能不能让一个固定权重的模型，根据自己真实执行任务时暴露出的弱点，提出并验证对自身 Harness 的修改？

整个过程不更新模型权重，也不需要更强的外部模型。

三种 Harness 改进范式

第一种是 Human Harness Engineering。人类专家检查执行日志，再手动修改 Harness。它有效，但高度依赖专家经验。

第二种是 Meta-Harness。一个更强的外部 Agent 观察目标 Agent 的表现，并替它优化 Harness。改进过程自动化了，但仍依赖外部优化器。

第三种就是 Self-Harness。目标 Agent 在当前 Harness 下运行，从自己的失败轨迹中学习，再由同一个模型提出有限、可验证的修改。

重点是把 Harness Improvement 变成可审计的状态转换：每次修改都要说明证据来源、修改位置、预期效果与验证结果。

和 Prompt Engineering 有的不同

Prompt Engineering 和 Context Engineering 通常改变输入文本、示例、记忆或检索内容。Self-Harness 修改的对象更广，是 Agent 的执行基座。

Reflexion 一类自改进方法，会把语言反馈保存下来，改变下一次回答策略；STOP 等方法改进生成程序；自动化 Agent 设计方法则从外部搜索 Agent 结构。

Self-Harness 研究的是一个更窄、也更可控的问题：同一个固定模型，能否在当前 Harness 下，提出对未来执行协议的 bounded edit，并通过回归测试决定是否采用。

三阶段循环

Self-Harness 的核心可以概括成三个阶段：Weakness Mining、Harness Proposal 和 Proposal Validation。

第一阶段：Weakness Mining

系统先让固定模型在当前 Harness 下运行 held-in 任务，收集执行轨迹与验证结果。

它不会把失败只粗略归类为“超时”或“缺少文件”，而是构建 verifier-grounded failure signature。每个失败签名至少区分三件事：验证器最终拒绝了什么、Agent 的行为如何导致这个结果、轨迹暴露了哪一种可复用的行为机制。

只有三个维度一致的失败轨迹，才会进入同一组。这样得到的不是表面症状，而是可能由 Harness 修改解决的重复性问题。

第二阶段：Harness Proposal

同一个模型切换到 proposer 角色，读取结构化的失败证据，并生成若干彼此不同、范围尽量小的候选修改。

每个 proposal 都必须对应具体的失败模式和可编辑位置，例如指令、工具策略、验证指导、记忆机制或运行时控制。它不能随意替换整个 Agent Controller。

第三阶段：Proposal Validation

每个候选 Harness 都要在 held-in 与 held-out 两组任务上重新测试。

接受规则非常保守：两个 split 都不能退化，并且至少有一个 split 必须提升。用公式表达就是：

Δin ≥ 0，Δheld-out ≥ 0，且 max(Δin, Δheld-out) > 0

通过验证的修改会合并到下一轮 Harness；未通过的修改只保留记录，不改变活跃版本。模型权重和 Evaluator 始终固定，只有 Harness 在演化。

四个关键设计

第一，失败分析必须有验证器证据。系统关心的是可复用的因果机制，不是看起来相似的错误描述。

第二，编辑范围必须预先声明。Proposer 只能修改明确开放的 Harness surface。

第三，每轮并行生成多个候选。不同方案分别测试，只有兼容且通过回归测试的修改才会被合并。

第四，全流程可审计。系统记录目标失败模式、修改位置、预期作用、split-wise 结果和最终的接受或拒绝决定，由此形成 Harness 的完整演化谱系。

Terminal-Bench-2.0 的效果？


实验选择三个不同家族的模型：MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5。

初始 Harness 被刻意保持得很简单：一个简短系统提示，加上 DeepAgent 默认的文件读取、写入、编辑与 Shell 工具。

任务被分成 held-in 和 held-out。Held-in 的执行轨迹与失败证据可以交给 Proposer；held-out 对 Proposer 完全不可见，只用于自动化的 promotion gate。每个候选 Harness 在两组任务上都会重复运行。

结果：不改权重，只改 Harness

MiniMax M2.5 的 held-out pass rate 从 40.5% 提升到 61.9%，绝对提升 21.4 个百分点，相对提升 53%。

Qwen3.5-35B-A3B 的 held-out 从 23.8% 提升到 38.1%，相对提升 60%；held-in 从 15.1% 提升到 36.0%，相对提升 138%。

GLM-5 的 held-out 从 42.9% 提升到 57.1%，绝对提升 14.2 个百分点，相对提升 33%。

视频所展示的 Terminal-Bench-2.0 结果中，三个模型的 held-out 均有提升，没有 split 出现退化。

这些数字说明两件事。

第一，Harness 层的修改可以在模型权重不变的情况下产生可测量的收益。

第二，held-out 的提升说明这些编辑不只是记住 held-in 的失败案例，而是捕捉到了一部分可复用的执行机制。

不同模型，学到不同的 Harness

Self-Harness 没有一套对所有模型都通用的万能提示词。不同模型保留下来的修改明显不同。

MiniMax M2.5 的修改更关注尽早创建必要的输出文件、正确处理结构化工具内容，以及在长时间工具循环后及时转向交付。

Qwen3.5-35B-A3B 更需要依赖项预检查、避免重复失败命令、从工具错误中恢复，以及在工件缺失时重新创建。

GLM-5 的修改则主要处理 Shell 环境的持续性，并推动 Agent 更快地从探索阶段转入实现和测试。

共同主题是 artifact reliability，但具体干预方式因模型而异。这正是论文强调“model-specific harness”的原因。

演化不是平滑上升

MiniMax M2.5 的演化轨迹显示，大多数候选修改都会被拒绝，只有少量通过验证门控的编辑被接受。

曲线并不会随着每一轮稳定上升。被拒绝的轮次不改变当前 Harness；被接受的修改则成为后续迭代的新起点。最终，MiniMax M2.5 在这组轨迹中的 pass rate 从 42.2% 提升到 53.9%。

保留下来的修改仍然非常局部：提前创建输出工件、增加对工具内容结构的处理规则、限制无效工具循环。它们改变了执行方式，却没有替换整体架构。

一个具体案例：从无尽探索转向完成任务

在 CountDataSetTokens 任务中，初始 Harness 下的 Agent 已经找到相关配置，却继续探索，最终超时，也没有创建要求的答案文件。

改进后的 Harness 让 Agent 在识别出目标数据子集后立即开始计算，将结果写入 answer.txt，并在停止前读回验证。

这里发生的变化不是模型突然“知道得更多”，而是 Harness 把工作流从持续探索推向了目标明确的生产与验证。

Qwen3.5-35B-A3B 的案例也类似。初始 Agent 在文件覆盖和编辑失败后反复重试，甚至删掉了验证器所需的关键文件；改进后的 Harness 会在连续工具错误后触发中间件，引导 Agent 改变策略、重建文件并检查最终输出。

GLM-5 的案例则显示，Harness 可以在长时间外部下载超时后推动 Agent 切换方案，先做小规模、分阶段验证，再修复未通过的检查。

这项工作的边界

Self-Harness 并不是没有限制的递归自我改进。

它只能修改预先声明的 Harness surface，不能无限制地发明新的控制架构。

它的接受规则高度依赖 Verifier。如果验证器带有噪声或覆盖不完整，系统就可能接受并不可靠的修改。

它研究的是 fixed benchmarks 下的 bounded edits，不是 open-ended self-improvement。当前结果证明的是：固定模型可以依据行为证据，参与改进包围自己的执行层；它并没有证明模型能够无限自我提升。

总结

Self-Harness 提供了一条不同于继续扩大模型参数的路线：先固定模型，再让 Agent 观察自己的失败，提出局部 Harness 修改，并用 held-out 回归测试决定是否接受。

当模型、评估器和任务协议保持不变时，我们能够更清楚地追踪性能变化究竟来自哪一次 Harness 修改。对真实 Agent 产品而言，这种可解释的演化谱系，可能比一次不可复现的 Prompt 灵感更有价值。

本期封面参考拉斯洛·莫霍利-纳吉（László Moholy-Nagy，1895—1946）的视觉语言。

他出生于匈牙利，1923 年进入包豪斯任教，并主持金属工坊；1928 年离开包豪斯。1937 年，他在芝加哥主持 New Bauhaus，把包豪斯关于艺术、技术与教育的实验带到美国。艺术家生平资料

莫霍利-纳吉长期研究摄影图（photogram）：不使用相机，而是把物体置于感光材料上，以光线直接留下透明、重叠与阴影的痕迹。摄影图资料 他还用金属、玻璃、塑料和电动结构制作《Light-Space Modulator》，让机器本身成为制造光影的装置。作品资料

这与 Self-Harness 有一个有趣的对应：工具不再只是被动媒介，而开始参与塑造过程本身。封面因此使用透明机械层、循环轨道与单一红色校准点，表现一个系统观察、验证并重组自身执行结构的过程。
