Insight 01

Always-on Agent 的 24 小时都在做什么？

⁠

用户关掉应用后，任务仍由云端的 Agent 继续处理。没有任务时，相关计算资源处于休眠；新消息或定时任务到来，恢复状态。需要浏览器或桌面操作时，​再启动供 Agent 使用的云端电脑。

⁠

唤醒 Agent 的入口不止于聊天框。Slack 消息、邮件、会议、定时流程或后台任务的结果，都可成为触发信号。路由层负责去重、排队，并把事件放进合适的对话。


邮件、网页和外部事件可能包含不可信内容，不能把它们当成用户指令。命令执行前可以由独立模型审查；发邮件等难以撤回的动作，需要让用户先确认，密码等敏感信息也应放在对话之外。

同时，也不再是每个任务完成都要通知用户。Lee 认为这是最考验产品设计的地方。

⁠
⁠

Insight 02

Grok Bot 存在于哪里？

⁠

Grok Bot 把处理消息、调用模型和安排任务的程序放在服务端。需要实际操作网页、文件或软件时，再调用一台独立的云端 Linux 虚拟机。


它相当于 Agent 的工作电脑，提供浏览器、文件和命令执行环境。

⁠

这台工作电脑可以独立关机、重建或升级。对话、记忆和任务进度另行保存，不必随它一起丢失。Firecracker 虚拟机的快照，则用于保存和恢复电脑本身的状态。

⁠

如此一来，任务执行到第三步时出了故障，恢复后应当从第三步继续。这里用到的是持久化工作流（durable workflow）：记录执行进度，支持故障后的恢复。Lee 团队使用了 Temporal 承担这部分能力。

⁠

任务的调度和进度另行保存，需要操作网页、文件或软件时，再调用云端工作电脑。

⁠
⁠

Insight 03

执行细节不进入主 Agent 的上下文

⁠

主 Agent 负责和用户对话、维护待办、协调任务。大量命令执行、文件读取或耗费上下文的工作，可以交给子 Agent；助手处理完后，把结果交回来。

⁠

这样，主对话不必装下每一次工具调用的细节。每个助手又可以拥有自己的持久化工作流，发生故障后单独恢复。长对话看起来能不断继续，依赖的是分工、压缩和检索；每个模型仍然有上下文上限。

⁠

工具也不必一开始就全部展开。先提供名称，需要时再读取具体说明和参数，可以给真正的任务留出更多上下文空间。调用工具时，优先选择可靠、成本较低的路径，再逐步使用浏览器或桌面操作。

⁠
⁠

Insight 04

方法写成 Skill，偏好存进记忆

⁠

反复执行的工作流程，可以写成 Skill，记录完成这件事所需的步骤和判断标准。个人偏好、近期发生的事、当前任务的临时细节，则进入不同层次的记忆。文件系统让这些信息能够按需搜索和读取。

⁠

•个人档案：需要持续记住的重要事实和偏好，随提示词一起提供。

⁠

•日期日志：保留发生过的事，把近期相关记录带进当前任务。

⁠

•临时笔记：保存眼下有用的细节，过时后可以淡出；其余信息需要时再搜索。

⁠

记忆告诉 Agent 过去发生过什么、用户有哪些偏好。读到的记忆仍是信息，不能自动变成新的执行指令。

⁠
⁠

Insight 05

面向提示词缓存优化

⁠

工具定义、系统提示等固定内容尽量放在稳定的前缀中，减少每轮变化，才能更好地利用提示词缓存。长输出保存到文件，耗费上下文的工作交给助手，主 Agent 留下推进任务需要的信息。

⁠

一个具体的工程建议是：提示词各部分的顺序要保持稳定。即便加入 A/B 测试的新提示，也不要打乱其他用户的提示词顺序；用户打开聊天框开始输入时，服务端还可以提前准备提示词，预热缓存。

⁠

对话变长后，还需要压缩和总结。用户暂时离开、缓存仍然有效时，可以先做整理，让下一轮从更短的摘要继续。

⁠

Insight 06

Agent 产品如何迭代

⁠⁠

Agent 出错后，把失败变成评估案例，修改运行框架、提示词或推理配置，再检查问题是否得到修复。模型训练则形成更长周期的迭代：让新模型学会使用工具、遵循约束，并在这些评估上持续改进。

⁠

模型进步后，原先为弥补能力不足而添加的界面和流程，也需要重新检查。


问题留在了长任务评估、记忆、安全和主动提醒的尺度上。持续数周或数月地可靠工作，仍是需要验证的方向。
