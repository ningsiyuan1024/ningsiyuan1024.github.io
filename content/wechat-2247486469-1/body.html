Harness Engineering本质上就是控制论

原文作者：George（@odysseus0z）｜文章字数：1609｜阅读时间：约 5 分钟

你将会得到

  • 理解 harness engineering 为什么不是新奇技巧，而是控制论在软件工程中的再次出现
  • 看清工程师角色如何从“直接执行”转向“设计反馈回路与约束系统”
  • 明白为什么代码库长期以来一直难以被自动化闭环接管
  • 学会判断 agent 失控时，问题更可能出在环境与标准外化，而不是模型能力不足

正文

读 OpenAI 关于 harness engineering 的文章时，我一直有一种熟悉感，却一时说不清来自哪里。直到突然想明白：这种模式我以前见过，而且不是一次，是三次。

第一次，是 18 世纪 80 年代 James Watt 的离心调速器。在它出现之前，工人必须站在蒸汽机旁边，手动调节阀门。它出现之后，一个带配重飞球的机械装置会感知转速，并自动调节阀门。工人并没有消失，只是工作变了：从亲手拧阀门，转为设计调速器。

第二次，是 Kubernetes。你声明一个期望状态——三个副本、这个镜像、这些资源限制。控制器会持续观察实际状态；一旦两者偏离，就开始做协调：重启崩溃的 Pod、扩缩副本、回滚失败部署。工程师的工作也随之变化：从手动重启服务，转向编写那份供系统持续校准的规格说明。

第三次，就是现在。OpenAI 描述了一类工程师：他们不再亲手写代码，而是设计环境、构建反馈回路、把架构约束编码进系统，再由 agent 去写代码。五个月里生成了一百万行代码，而人工一行未写。他们把这种工作叫作 “harness engineering”。

这三次里，模式始终相同。1948 年，Norbert Wiener 给它命名为 cybernetics，词源来自希腊语 κυβερνήτης，意思是“舵手”。你不再亲手拧阀门，你是在掌舵。

每当这种模式出现，背后都意味着：有人终于造出了足够强的传感器和执行器，得以在那个层级闭合反馈回路。

为什么代码库一直是最后的例外

代码库其实一直都有反馈回路，只不过大多停留在较低层级。编译器能在语法层闭环；测试套件能在行为层闭环；linter 能在风格层闭环。这些都是真正的控制系统——但它们只能作用于那些可以被机械检查的属性：能不能编译？能不能通过测试？有没有遵守规则？

而更高一层的问题——这次改动是否符合系统架构？这个方案是不是正确方向？这个抽象会不会随着代码库变大而引发问题？——过去既没有传感器，也没有执行器。只有人类能在这个层面同时承担两件事：判断质量，以及动手修正。

LLM 一次性改变了这两端。它既能像过去的人类那样，在高层级“感知”问题；也能在同一层级“行动”：重构模块、重新设计不一致的接口、围绕真正重要的契约重写测试套件。第一次，反馈回路可以在真正关键决策发生的地方闭合。

但闭环是必要条件，不是充分条件。Watt 的调速器需要调校；Kubernetes 的控制器需要正确的 spec；而让 LLM 在你的代码库上工作，则需要提供一种更难给出的东西。

如何校准传感器与执行器

把最基础的反馈回路搭起来——让 agent 能运行测试、让 CI 给出可解析的输出、让报错信息足够指向修复路径——这些都只是最低门槛。Carlini 在让 16 个并行 agent 构建一个 C 编译器时，已经证明了这一点：提示词极其简单，但测试基础设施设计得非常到位。“我大部分精力都花在为 Claude 设计周边环境上：测试、执行环境、反馈机制。”

更难的是：如何用你这个系统特有的知识，去校准传感器与执行器。大多数人卡住的地方在这里，然后他们把责任归咎于 agent。

“它总是在做错事。它根本不理解我们的代码库。” 这个诊断大多数时候都是错的。agent 失败，并不是因为它能力不够，而是因为它所需的知识——在你的系统里，什么叫“好”；你的架构奖励什么模式、回避什么模式——全都还锁在你的脑子里，而你并没有把它外化出来。agent 不会靠耳濡目染学会这些。如果你不把它写下来，第 100 次运行时它犯的错误，会和第 1 次一模一样。

真正的工作，是把你的判断变成机器可读。写出真正描述分层和依赖方向的架构文档；编写附带 remediation instruction 的自定义 linter；沉淀出能编码团队审美与偏好的 golden principles。OpenAI 发现的也是同一件事：他们原本每周五都要花 20% 的时间清理 “AI slop”，直到他们把标准编码进 harness 本身。

唯一的出路

这套实践所要求的东西——文档、自动化测试、被编码的架构决策、快速反馈回路——其实一直都是正确的。过去三十年里，几乎每一本工程书都在强调这些。很多人之所以跳过，不过是因为跳过它们的代价过去来得慢、也分散：质量缓慢下滑、上手成本增加、技术债在沉默中复利。

而 agentic engineering 把这种代价放大到了极端。没有文档，agent 就不会遵守你的约定——而且不是在一个 PR 里出错，而是在每一个 PR 上，以机器速度、全天候地持续偏离。没有测试，反馈回路根本无法闭合。没有架构约束，漂移会以快过你修复速度的方式持续累积。更危险的是：如果 agent 根本不知道“干净”长什么样，你甚至无法再用 agent 去清理这团混乱。没有校准，那些制造问题的机器，也不可能反过来解决问题。

实践本身没有变，变得无法承受的是忽视它们的代价。

生成—验证不对称——这是 P vs NP 背后的直觉，也被 Cobbe 等人对 LLM 的实验结果所印证——实际上指明了未来方向：生成一个正确答案，比验证一个答案是否正确更难。你不需要在实现上胜过机器，你需要在评估上胜过它：把“正确”定义清楚，在输出偏离时识别出来，判断方向是否真的对。

那些设计出 Watt 调速器的人，并没有再回去亲手拧阀门。不是因为他们不会，而是因为那样做已经没有意义了。
