1. Agent Loop 的运作

Trace 与 Turn：

  • Trace：这里用它表示从用户输入一个问题，到 Agent 完成本次处理并最终答复的完整过程。这是便于理解的过程划分，不表示 Pi 会话文件里存在一层同名的树节点。
  • Turn：一次 LLM 响应，加上这次响应触发的工具调用与工具结果。每个 Turn 可以拆成模型调用、工具执行两个环节，其中工具执行是可选的。
举例来说：
Session └─ Trace（一次任务的概念示意） ├─ Turn 1 │ ├─ Assistant Message │ ├─ Tool Call │ └─ Tool Result ├─ Turn 2 └─ Turn 3

2. Context Engineering

基本上下文组件：

  • systemPrompt

  • tool schemas

2.1 Session

Pi 里的 Session 使用 JSONL 保存完整历史，并通过 id 和 parentId 构成一棵树，但是不会全部发送给模型。
例如：
A — B — C \ D — E
用户通过 /tree 从 C 切换到 E 时，Pi 可以对离开的分支进行总结：
分支 B-C 尝试了方案一： - 修改了 parser.ts - 测试失败 - 失败原因是……
然后将这个 Branch Summary 注入目标分支。
流程包括：
  1. 找到两个分支的共同祖先；
  2. 收集离开分支上的消息；
  3. 生成摘要；
  4. 在目标位置加入 BranchSummaryEntry。
这样切换分支后，模型不会完全忘记另一个分支上得到的结论。

2.2 Turn

每个 Turn 发起模型调用前，Pi 可以通过 transformContext 动态变换上下文，再通过 convertToLlm 转成模型兼容格式。
AgentMessage[] ↓ transformContext ↓ convertToLlm ↓ Message[] ↓ Provider Payload
  • transformContext：在 Agent Message 层处理上下文
  • convertToLlm：transformContext 之后，Pi 再使用 convertToLlm 把内部消息转换为模型兼容格式
同一次用户输入引出的任务特别长时：
即使没有新的 User Message，Agent 也可能连续经历多个 Turn，并执行大量工具。这整段消息跨度可能超过保留预算。
Pi 允许在这段跨度内部、Assistant Message 所在的位置切分。这种情况下，会分别总结：
  • 更早的历史
  • 当前这段长任务中、切分点之前的消息
*不能在 Tool Result 切分。因为 Tool Result 和 Tool Call 必须保持一致。
2.3 Compaction 上下文压缩
本质是将长对话压缩成一个任务快照。
压缩流程：
  1. 判断是否达到自动压缩阈值：contextTokens > contextWindow - reserveTokens。
  2. 从最新消息向前计算需要保留的上下文，按 keepRecentTokens 预算寻找切分点。
  3. 选择较旧消息作为待总结内容
  4. 调用 LLM 生成结构化摘要
  5. 保存 CompactionEntry
  6. 重新构建 Context
  7. 用摘要＋最近消息继续工作
压缩前：
System Prompt 消息 1 消息 2 消息 3 ... 消息 100
压缩后：
System Prompt 历史摘要 消息 81 消息 82 ... 消息 100
模型最终看到的：
  • System Prompt
  • 历史摘要
  • 最近消息
  • 最近工具结果

3.1 延迟加载工具设计

工具定义的延迟加载取决于所用的 Pi 版本、Provider 及模型接口支持。可以按这个思路理解两类工具定义：
  • immediate tools：立即发送完整定义
  • deferred tools：延迟加载或通过工具引用暴露
大致思路类似 skills 的渐进式加载：
先提供少量核心工具 → 模型需要特殊工具 → 再加载特殊工具。具体调用方式需要对照所用的 Pi 版本和 Provider，不能假设所有模型接口都采用相同机制。

3.2 注意事项

  1. 只靠 prompt 无法保证安全，真正的安全边界必须在 runtime。
比如：参数校验、路径限制、命令 allowlist / denylist、系统权限、沙箱
2. 控制工具输出大小
  • 截断长输出
  • 将完整输出保存到文件，返回摘要或关键内容。
  • 提供关键行号
  • 保留可继续读取的路径
