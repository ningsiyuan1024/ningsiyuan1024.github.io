提取发票字段和推进一项跨代码仓库、数据库、外部接口的任务，对模型的要求显然不同。选哪款模型只是第一步，接下来还要决定：给它多少推理资源，哪些操作可以自主完成，以及怎样检查最后的结果。

⁠

OpenAI 在 10 月 2 日发布的 GPT-6 实用指南，将这些问题放进了同一套工作流程。它给出的一个重要出发点是：用真实任务，同时比较成功率、耗时和每次成功完成任务的成本。

⁠

具体到执行中，更高的推理强度需要额外的时间和费用；缓存能降低重复输入的费用，完整任务的成本还要计入输出等开销；长任务可以并行推进，依赖工具结果的步骤仍然需要等待。这些取舍都要结合任务本身判断。

⁠

对准备把 GPT-6 接入实际工作的团队来说，值得追问的是：怎样把模型、指令、工具和人工判断接成一个能持续推进、也便于核查的工作流？

⁠/⁠

Insight 01

如何选模型，才能兼顾能力与交付成本？

⁠

1.部署前，先用有代表性的真实任务评估工作流，同时记录成功率、耗时，以及每次成功完成任务的成本。这三个指标一起看，才能判断一种方案是否适合投入使用。

⁠

2.三款模型对应不同的工作负载，选择时需要结合具体任务的表现与价格：

⁠

•GPT-6 Astra：面向最困难、最依赖推理能力的工作。

⁠

•GPT-6.1 Sol：覆盖复杂编程、研究和计算机使用等任务。

⁠

•GPT-6 Luna：面向目标明确、需要大规模重复执行的任务，例如发票字段提取、请求分类和结构化摘要。

⁠

Insight 02

成本、推理强度和响应速度，怎样分别调整？

⁠

复用上下文，降低重复工作成本

⁠

4.模型选定后，重复任务可以通过提示词缓存复用共用内容。缓存能否被复用，也与输入的组织方式有关：

⁠

•把固定指令和参考资料放在可变的任务信息之前，并保持工具定义稳定。

⁠

•缓存输入相对未缓存输入的费用最多可低 95%，具体幅度取决于模型。

⁠

这里的 95% 指缓存输入的费用降幅，不能直接推算为整个工作流程节省 95%。完整成本仍取决于输入、输出及适用的其他费用。

⁠

5.上下文也需要取舍：删去当前任务用不到的信息，同时保留必要依据。较长的对话可以压缩上下文，但要留下继续执行所需的状态。

⁠

•投入生产前，还要确定如何监控模型行为，并检查应用的数据控制措施。

⁠

推理强度与生成速度分开调整

⁠

6.推理强度应随任务难度变化。先选择适合当前工作的档位，再判断增加的推理资源是否值得：

⁠

•低档：事实提取、小幅修改等常规任务。

⁠

•中档：需要判断的工作，例如规划功能、比较方案。

⁠

•高档：困难调试、深入分析或细致审查。

⁠

•更高档位：仅在高档仍不够、且模型支持时测试。只有效果提升足以抵偿额外的时间和费用，才保留使用。

⁠

7.API 和 Codex 提供不同的调整入口：

⁠

•在 API 中，可以在对话过程中改变推理强度，且不会使缓存失效。

⁠

•在 Codex 中，可以从模型默认档位开始，再根据任务复杂度上调或下调。

⁠

8.响应速度是另一项设置，需要单独比较收益与费用：

⁠

•API 的 Fast 模式适合对响应时间敏感的应用，代价是更高的每 token 费用。

⁠

•GPT-6 Astra 的 Ultrafast 可在 Codex 和 API 中加快 token 生成，但不改变推理强度，也需要为更快的响应额外付费。

⁠

Insight 03

提示词和技能，需要把边界写清到什么程度？

⁠

9.资源设置之外，任务本身也要交代清楚：想要什么结果、面向谁、有哪些背景与限制，以及什么算作完成。模型理解模糊含义的能力增强后，过去依赖的过细指令，也可能限制它处理任务的空间。

⁠

10.技能的入口与补充内容承担不同作用：

⁠

•用简短描述说明技能何时触发，只在需要时加载补充细节。

⁠

•提供适合所用模型的指导原则，减少僵硬的逐步流程。

⁠

11.代码仓库中的 AGENTS.md 要说明文档和测试的适用条件，并明确哪些日常操作已经得到授权。

⁠

OpenAI 给出的例子是：允许使用一次性数据运行本地测试，同时明确该流程不访问生产环境。操作内容与适用边界需要一起写清。

⁠

12.决策边界和完成标准需要一起说明。模型应知道哪些选择可以自行做，哪些变化需要交给人判断。

⁠

•把实施、运行、检查和修复写进完成标准，让任务推进到结果经过检查，而不只停留在实施改动。

⁠

•交付说明应包含做了什么、验证了什么，以及还有哪些事项需要关注。

⁠
⁠

Insight 04

任务运行数小时，如何在途中纠偏并继续推进？

⁠

13.初始指令写清之后，长任务仍可能需要途中调整。在 API 中，可以通过 Responses WebSocket API，把新的要求送入正在执行的任务。

⁠

•这些更新会进入队列，不会取消已启动的工具，也不会撤销先前完成的操作。

⁠

14.异步工具调用可以减少等待慢步骤时的空转，但前提是工作之间没有依赖。

⁠

•等待测试等慢步骤时，模型可以继续处理其他独立工作。

⁠

•如果下一步必须使用工具结果，就应等结果返回后再开始。

⁠

15.可以独立拆分的任务，也可以委派给子智能体。GPT-6.1 Sol 支持通过 Responses API 分别调查代码库的不同部分，再汇总发现；截至 2026 年 10 月 2 日，这项多智能体功能仍处于测试阶段。

⁠

16.在 Codex 中，GPT-6 Astra 可以在执行过程中请求澄清。用户需要解决影响下一步的关键问题，并交代等待期间的安排：

⁠

•说明哪些独立工作可以继续，避免所有工作都停在同一个决定上。

⁠

•暂时离开时，交代哪些任务可以继续，以及何时应暂停等待答复。

⁠

17.需求发生变化时，就在当前任务中补充新信息，明确哪些地方需要调整、哪些仍沿用原来的要求，避免继续推进已经偏离需求的方案。

⁠
⁠

Insight 05

计算机使用如何接入工作流，交付怎样的结果？

⁠

18.执行与检查可以衔接在同一个流程里。GPT-6 Astra、GPT-6.1 Sol 和 GPT-6 Luna 可以操作网站与桌面应用，包括没有 API 的软件；例如调查问题、修改代码，再打开产品检查修复是否生效。

⁠

19.每个环节都应选择适合的执行入口：能用 API 或已连接工具直接完成，就使用这些入口；需要读取屏幕、点击或填表，再使用计算机操作。

⁠

•集成到自己的应用时，可以给模型提供通过代码控制浏览器或桌面的工具，例如用于浏览器的 Playwright、用于桌面的 PyAutoGUI。

⁠

20.交付中可以同时包含结果和检查依据。OpenAI 收录的 GPT-6 Astra 客户案例中，Cognition 与 Hex 展示了两种做法：

⁠

•Cognition：在一个 iPhone 游戏测试案例中，Devin 提供模拟器录屏与测试报告，区分已通过的检查和没有测试的部分，便于工程师继续核查。

⁠

•Hex：将销售渠道问题转成书面分析与交互式仪表板，包含地区维度的拆分；同时让模型检查数据是否合理、分析是否回答了业务问题。

⁠

21.交付形式还要适应已有工作流程。同一组客户案例中的 Harvey 和 Invideo，分别把模型用于文稿与视频剪辑：

⁠

•Harvey：把法院资料、判例、律所文档和律师偏好组合起来，用于定制法律文稿。

⁠

•Invideo：用模型安排时间线剪辑，并生成剪辑师可以继续修改的特效。据该公司报告，调色与色彩校正任务的成功率约为此前的三倍。
