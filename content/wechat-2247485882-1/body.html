MCP 已死，CLI 万岁

2026 年 2 月 28 日

字数：约 2,500 字｜阅读时间：约 7 分钟

- LLM 本来就很擅长使用命令行工具（CLI），未必需要一套新协议
- CLI 对人和智能体都友好：更易调试、更可组合，认证体系也更成熟
- MCP 仍可能有价值：当某个工具确实没有 CLI 等价物时
一句话结论：与其投入资源做 MCP server，不如先把 API 与 CLI 做好，让智能体自己“学会用”。

我要抛出一个大胆观点：MCP 已经在走向死亡。我们可能还没有完全意识到，但迹象已经很明显了：OpenClaw 不支持它，Pi 不支持它——而且理由充分。

当 Anthropic 宣布 Model Context Protocol（模型上下文协议，MCP）时，整个行业几乎集体“上头”。每家公司都急着发布 MCP server，用来证明自己是“AI first”。巨量资源被砸进新的端点、新的传输格式、新的鉴权方案——就为了让 LLM 去和那些它本来就能对话的服务“对话”。

我承认，我一直没完全理解它的必要性。你知道 LLM 最擅长什么吗？它们很擅长自己把事情摸清楚。给它一个 CLI 和一份文档，它们就能直接起飞。

我拖了很久才写这篇，但我越来越确信：MCP 在真实世界里并没有带来任何实质收益，我们甚至会因为它而变得更糟。让我解释一下。

LLM 不需要一个特殊协议

LLM 非常擅长使用命令行工具。它们的训练数据里有数百万份 man page、Stack Overflow 答案，以及 GitHub 上成堆的 shell 脚本。当我让 Claude 去跑 gh pr view 123，它就是能用，而且往往一次就成功。

MCP 承诺的是更“干净”的接口，但在实践中我发现：我依然要写同样的文档——每个工具是干什么的、有哪些参数，更重要的是：什么时候该用它。LLM 并不需要一个新协议来理解这些。

CLI 也是给人用的

当 Claude 用 Jira 做了点出乎意料的事情时，我可以自己跑同一个命令，比如 jira issue view，看它到底看到了什么。同样的输入，同样的输出，没有谜题。

但如果用 MCP，这个工具“只存在于 LLM 对话里”。出了问题，你就不得不去翻 JSON 传输日志，而不是直接自己跑一遍命令看结果。调试不应该需要一个协议解码器。

可组合性（Composability）

这里差距会被拉得非常大。CLI 天生可组合。我可以 pipe 给 jq，可以用 grep 串起来，可以重定向到文件。它不只是“方便”，很多时候甚至是唯一实际可行的办法。

比如要分析一个很大的 Terraform plan：

terraform show -json plan.out | jq '[.resource_changes[] | select(.change.actions[0] == "no-op" | not)] | length'

如果用 MCP，你的选择通常只有两个：

1. 把整个 plan 倒进 context window（昂贵，而且经常根本不可能）；
2. 在 MCP server 里自己实现自定义过滤逻辑。

无论哪一种，你都在做更多工作，却得到更差结果。CLI 的做法则是复用现成工具：它们早就存在、文档完善，而且人和 agent 都能读懂。

认证（Auth）本来就好用

MCP 在认证这件事上过度“有主张”。但我想问：一个“让 LLM 使用工具”的协议，为什么要强行把认证也包进去？

CLI 工具根本不在乎：

  • aws 用 profiles 和 SSO
  • gh 用 gh auth login
  • kubectl 用 kubeconfig

这些都是经受多年考验的认证流程。无论是我自己敲键盘，还是 Claude 在“驾驶”，它们的工作方式都一样。认证坏了，我也用一直以来的方式修：aws sso login、gh auth refresh。不需要任何 MCP 专属排障。

更少的运转部件（No moving parts）

本地 MCP server 是进程。它需要启动、需要常驻、还不能默默挂死。在 Claude Code 里，它们通常作为子进程被拉起——有时好用，但并非总是如此。

CLI 工具只是磁盘上的二进制文件：

没有后台进程、没有状态要管、没有初始化仪式。你需要它时它就在，不需要时它完全“隐身”。

现实中的痛点（The practical pain）

除了设计理念，MCP 在日常使用中确实带来了很多摩擦：

  • 初始化很不稳定。我已经数不清因为某个 MCP server 没起来而重启 Claude Code 的次数。有时候重试就好，有时候要清状态、从头来过。
  • 反复 re-auth 没完没了。用多个 MCP 工具？那就准备好每个都要重新授权。相比之下，带 SSO 或长效凭证的 CLI 没这毛病：认证一次就结束。
  • 权限要么全给、要么全不给。Claude Code 允许你按名字 allowlist MCP 工具，但也就到此为止了。你没法限制成“只读操作”，也没法限制参数范围。

而用 CLI，我可以 allowlist gh pr view，但对 gh pr merge 要求额外审批。这种粒度很重要。

那 MCP 什么时候有意义？

我不是说 MCP 完全没用。如果一个工具真的没有任何 CLI 等价物，那 MCP 可能是正确选择。在我的日常里也确实还在用一些 MCP——因为它是唯一可用选项。

我甚至愿意承认：标准化接口这件事可能有价值，而且一定存在一些 use case，让它比 CLI 更合理。

但对绝大多数工作来说，CLI 更简单、更好调试、更可靠。

真正的教训（The real lesson）

最好的工具，是既能给人用，也能给机器用的工具。CLI 已经迭代了几十年：可组合、可调试、并且天然复用已经存在的认证系统。

MCP 试图建立一个更好的抽象。结果发现：我们其实早就有一个挺好的抽象了。

给构建者的一点请求（A plea to builders）

如果你是一家公司：正在投入资源做 MCP server，但你甚至没有一个官方 CLI——请停下来，重新想想你在做什么。

先把 API 做好，再把 CLI 做好。智能体会自己搞定剩下的。
