Agent Harness 才是真正的产品（而不是模型）

字数：约 2,800 字｜预计阅读：约 8 分钟｜来源：X （@hxlfed14）

1）为什么“模型不是产品，Harness 才是”

很多人都在讨论 models，但很少人讨论 scaffolding（脚手架/支架/运行时）。

作者的核心论点是：最好的 Agent 产品正在收敛到同一套“外壳”工程：

  • 一个刻意保持简洁的执行循环（loop）
  • 少量“原语级”工具（primitive tools）给模型手和眼
  • Harness 负责：什么时候把什么信息给模型、允许它做什么、失败了怎么恢复

因此结论非常直接：模型是可替换的（interchangeable），Harness 才是产品本体。

作者给的直觉是：同一个模型，换一套 scaffold / harness，效果可能直接翻倍；反之，工具越堆越多并不一定更强，很多时候反而更不稳定、更耗 token、更慢。

一句话：你以为你在做 AI，其实你在做“运行时工程 + 可靠性工程”。

2）Harness 到底是什么

在这篇文章里，Agent harness 指的是“模型之外、让模型在真实世界可用的一切东西”，包括但不限于：

  • 执行循环（execution loop）
  • 工具定义与调用协议（tool definitions / tool calling）
  • 错误处理与重试语义（error recovery / retries）
  • 状态与进度管理（state / checkpoint / todo）
  • 信息流与上下文分层（information flow / context layering）
  • 权限与边界（什么能自动执行、什么需要审批）
  • 观测与可追踪性（tracing / logs / replay）

模型负责“想做什么”；harness 负责“它能看到什么、能做什么、失败时系统如何响应”。

3）生产级 Agent 的共同祖先：那条循环

作者认为，几乎所有生产 Agent 最后都会长得像下面这条循环（伪代码）：

while (模型持续返回 tool calls):
  执行工具
  捕获结果（含错误）
  追加到上下文
  再调用模型

关键点在于：复杂性不在 loop 本身，而在 loop 周围的工程化外壳。

同样是 while(tool_call)，不同产品体验差很多，本质是它们的“外壳”差很多。

4）各家系统的 Harness：代表性的几种路线

下面按原文提到的代表系统，整理它们的 Harness 设计要点（为了公众号阅读做了结构化，但不改变观点）。

4.1 Claude Code：模型控制循环（The Model Controls the Loop）

核心立场：不是“代码控制模型”，而是“模型控制 loop”。

典型特征：

  • 结构：扁平消息列表（flat message list）+ 一组原语工具
  • 循环：本质就是 while(tool_call)，尽量不搞复杂 DAG 编排
  • 工具哲学：偏好“原语 > 集成”
  • 命令行探索：bash / grep / glob 等
  • 文件交互：read / write / edit / multi-edit
  • 搜索与抓取：web search / fetch
  • 进度管理：todo / task

信息分层：让上下文“按层加载”

作者强调“上下文工程”不是把所有东西塞满，而是分层加载，例如：

  • 组织/安全策略
  • 项目级设置
  • 用户偏好
  • 会话历史
  • git 状态等

并且会在工具结果里附带固定的系统提醒文本（用“每次 tool call 后重复强化”的方式稳定行为边界）。

错误恢复：TODO 不是功能，而是进度锚点

工具失败会把错误作为结果返回给模型，让模型自己选择下一步。

而类似 TodoWrite 的价值在于：

  • 强迫 Agent 外显计划
  • 任务跑长/中途失败时，能快速恢复“我做到哪一步了”

这类“看起来像工具，实际上是 Harness 技巧”的设计，对长链路任务非常关键。

4.2 Cursor：文件是第一原语（Files as the Fundamental Primitive）

作者把 Cursor 的思路概括成一句话：Everything maps to files.

为什么把“文件”作为上下文原语？这是很工程化的理由：

  • 文件天然可搜索（grep/ripgrep/jq/语义检索）
  • 天然可分组（按目录/模块/权限边界）
  • 天然可版本化（可 diff / 可回滚）
  • 比“再造一个抽象层”更安全、更可控

语义搜索：用 Agent 运行轨迹训练检索

作者提到一种思路：用 agent session traces 做训练数据——回放成功任务，反推出“哪些文件其实应该更早被取出”，让检索模型学习这种模式。

4.3 Manus：KV-Cache 至上（KV-Cache Above All Else）

作者把 Manus 的经验总结成：token 经济学决定架构。

当 input:output token 比例极端（例如 100:1）时，如果你在上下文最前面频繁改动大块内容（例如工具定义），KV-cache 很容易失效，成本会非常高。

于是 Manus 的路线是：

  • 工具常驻（尽量避免“动态增删工具定义”）
  • 用 logit masking 在解码阶段限制“本轮允许用哪些工具”
  • 工具命名采用统一前缀分组（便于做 mask）

分层动作空间：把复杂工具从上下文里挪出去

作者描述一种三层动作空间的设计：

1. Level 1：原子 function-call 工具
2. Level 2：通过 shell 调用的沙盒工具（复用现成命令行生态）
3. Level 3：动态脚本（现场写小程序）

目标是：能力要保留，但尽量别把长工具定义塞爆上下文。

作者给的“最大教训”非常尖锐：

很多性能提升来自“删东西”——减少复杂工具、减少管理型代理、减少无必要的上下文注入。

4.4 SWE-Agent：为 Agent 设计的计算机接口（ACI）

作者强调 SWE-Agent 的贡献点：提出 ACI（Agent-Computer Interface） 概念——给 LLM Agent 设计的接口，不一定是给人设计的 UI/CLI。

典型 Harness 技巧：

  • Linter 把关编辑：不通过就拒绝，让它重试
  • 观测压缩（observation compression）：保留最新关键观测，其余压缩成单行摘要
  • 本质是把“渐进式披露”写进 loop 里

5）最关键模式：渐进式披露（Progressive Disclosure）

作者认为这是区分“可用 Agent”与“炫技 Demo”的关键。

它来自 UI/UX：只展示当下需要的信息，复杂性按需展开。映射到 Agent 上就是：

  • 不要把所有文档/工具/上下文一次性塞进窗口
  • 让 Agent 按需发现、按需加载、按需压缩
  • 把最新检索到的关键信息放在上下文末尾（更容易被模型有效利用）
  • 把“中间大量无关噪声”从上下文里剔除或压缩
结论：上下文不是越多越好，而是“何时给、给什么、给多少”。这就是 Harness 的工作。

6）工程结论：把资源花在 Harness 上

作者最后的收束观点可以压成三句：

1. 别把“换更强模型”当作主要杠杆；把工程资源投到 Harness 才会持续复利
2. 渐进式披露不是锦上添花，而是生产级 Agent 的架构必需
3. 随着模型变强，Harness 应该变得更简单（更少工具、更少上下文噪音），而不是更复杂

7）术语对照（方便转发）

  • Harness / Scaffolding：代理运行时支架/脚手架（模型之外让系统可用的那层）
  • Primitive tools：原语级工具（尽量少、尽量通用）
  • Progressive disclosure：渐进式披露（按需加载/压缩信息）
  • KV-cache：解码缓存（前置上下文变化会导致缓存失效）
  • Logit masking：对输出分布做约束（限制本轮允许的 action/tool）
  • ACI：Agent-Computer Interface（为 agent 设计的交互接口）
