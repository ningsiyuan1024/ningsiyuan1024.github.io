这是一篇关于智能体外壳（agent harness）的深度拆解。原文讨论了 Anthropic、OpenAI、Perplexity、LangChain 等团队到底在构建什么：编排循环、工具、记忆、上下文管理，以及一切把无状态大语言模型变成可用智能体的软件基础设施。

你可能已经做过聊天机器人，也可能接过几个工具，跑通了一个 ReAct 循环。Demo 看起来没问题。可一旦要做生产级系统，问题很快出现：模型忘了三步前做过什么，工具调用悄悄失败，上下文窗口被杂音填满。

问题不在模型本身，而在模型周围的一切。

LangChain 做过一个很有说明力的实验：模型和权重不变，只换掉包裹 LLM 的基础设施，TerminalBench 2.0 排名就从 30 名开外跳到第 5。另一个研究项目让 LLM 自己优化这层基础设施，最终 pass rate 达到 76.4%，超过了人工设计的系统。

这层基础设施现在有了名字：智能体外壳（agent harness）。

什么是Agent Harness

这个词在 2026 年初被正式化，但概念早就存在。外壳是包裹 LLM 的完整软件基础设施：编排循环、工具、记忆、上下文管理、状态持久化、错误处理和护栏。

Anthropic 的 Claude Code 文档把 SDK 称为“驱动 Claude Code 的 agent harness”。OpenAI 的 Codex 团队也用类似说法，把“agent”和“harness”都指向让 LLM 变得有用的非模型基础设施。

LangChain 的 Vivek Trivedy 有一句很直接的话：

如果你不是模型，你就是 harness。

很多人容易在这里混淆。“Agent”是用户感知到的涌现行为：一个有目标、会用工具、能自我纠错的实体。“Harness”是产生这种行为的机器。

所以，当有人说我做了一个 agent，更准确地说，是他做了一个外壳，然后把它接到了某个模型上。

Beren Millidge 在 2023 年的文章《Scaffolded LLMs as Natural Language Computers》中给过一个很贴切的类比：裸 LLM 就像一颗没有内存、没有硬盘、没有 I/O 的 CPU。

上下文窗口像内存，速度快但空间有限。外部数据库像硬盘，容量大但访问慢。工具集成像设备驱动。Harness 就是操作系统。

Millidge 的说法是：我们重新发明了冯·诺依曼架构，因为这本来就是任何计算系统都会自然走向的抽象。

三层工程

模型外面有三层同心圆。

Prompt engineering 负责写模型收到的指令。

Context engineering 负责管理模型在什么时候看到什么。

Harness engineering 包含前两者，还包括完整的应用基础设施：工具编排、状态持久化、错误恢复、验证回路、安全约束和生命周期管理。

Harness 不是 prompt 的包装。它是让自主智能体行为成为可能的完整系统。

生产级外壳的 12 个组件

综合 Anthropic、OpenAI、LangChain 和开发者社区的实践，一个生产级 agent harness 通常包含 12 个组件。

1. 编排循环（orchestration loop）

这是整个系统的心脏。它实现的是 Thought-Action-Observation 循环，也就是常说的 TAO 或 ReAct loop。

流程大致是：

组装 prompt，调用 LLM，解析输出，执行工具调用，把结果喂回模型，然后重复，直到任务完成。

机械地看，它往往只是一个 while 循环。复杂度不在循环本身，而在循环所管理的一切。Anthropic 把自己的运行时描述为“笨循环”：智能都留在模型里，harness 只负责管理轮次。

2. 工具（tools）

工具是智能体的手。它们以 schema 的形式定义，包括名称、描述和参数类型，然后被注入到 LLM 的上下文中，让模型知道自己能调用什么。

工具层要处理注册、schema 校验、参数提取、沙箱执行、结果捕获，以及把执行结果格式化成模型能读懂的 observation。

Claude Code 的工具覆盖六类：文件操作、搜索、执行、Web 访问、代码智能和子智能体派生。OpenAI Agents SDK 支持 function tools、hosted tools，以及 MCP server tools。

3. 记忆（memory）

记忆有不同时间尺度。

短期记忆是单次会话中的对话历史。长期记忆会跨会话持久化：Anthropic 使用 CLAUDE.md 项目文件和自动生成的 MEMORY.md，LangGraph 使用按 namespace 组织的 JSON Stores，OpenAI 支持由 SQLite 或 Redis 承载的 Sessions。

Claude Code 使用三层结构：始终加载的轻量索引、按需读取的主题详情文件，以及只能通过搜索访问的原始 transcript。

一个关键原则是：agent 只能把自己的记忆当作提示，行动前必须回到真实状态中验证。

4. 上下文管理（context management）

很多 agent 会在这里静默失败。核心问题是 context rot：当关键信息落在上下文窗口中间位置时，模型性能会明显下降。Chroma 的研究显示下降幅度超过 30%，也和 Stanford 的 Lost in the Middle 发现相互印证。

即使有百万 token 窗口，随着上下文增长，指令遵循能力也会退化。

生产中的常见做法包括：

  • 压缩（compaction）：接近上限时总结历史。Claude Code 会保留架构决策和未解决 bug，丢弃冗余工具输出。
  • Observation masking：JetBrains Junie 会隐藏旧工具输出，但保留工具调用本身。
  • 即时检索（just-in-time retrieval）：只保留轻量标识符，需要时再加载。Claude Code 使用 grep、glob、head、tail，而不是直接读完整文件。
  • 子智能体委派（sub-agent delegation）：子 agent 可以充分探索，但只把 1000 到 2000 token 的浓缩摘要返回给父 agent。

Anthropic 对上下文工程的目标说得很清楚：找到最小的高信号 token 集合，让期望结果出现的概率最大。

5. Prompt 装配(prompt construction）

这一层决定模型每一步实际看到什么。

Prompt 是分层组装的：系统提示、工具定义、记忆文件、对话历史，以及当前用户消息。

OpenAI Codex 使用严格的优先级栈：服务端控制的系统消息优先级最高，然后是工具定义、开发者指令、用户指令，包括级联的 AGENTS.md 文件，再往后是对话历史。

6. 输出解析（output parsing）

现代 harness 主要依赖原生工具调用。模型返回结构化的 tool_calls 对象，而不是让系统从自由文本里硬解析。

Harness 要判断：有工具调用吗？有就执行并回到循环。没有工具调用，就把当前输出当作最终答案。

对于结构化输出，OpenAI 和 LangChain 都支持通过 Pydantic 模型做 schema 约束。像 RetryWithErrorOutputParser 这样的旧方法仍然有用：它会把原始 prompt、失败输出和解析错误一起喂回模型，让模型修正。

7. 状态管理（state management）

LangGraph 把状态建模为在图节点之间流动的类型字典，用 reducer 合并更新。Checkpoint 会发生在 super-step 边界，因此系统可以在中断后恢复，也可以做 time-travel debugging。

OpenAI 提供四种互斥策略：应用内存、SDK sessions、服务端 Conversations API，以及轻量的 previous_response_id 链接。

Claude Code 的方式不同：把 git commits 当作 checkpoint，把 progress files 当作结构化草稿纸。

8. 错误处理（error handling）

错误会快速累积。一个 10 步流程，如果每一步成功率都是 99%，端到端成功率也只有大约 90.4%。

LangGraph 区分四类错误：

  • 短暂错误：用 backoff 重试。
  • LLM 可恢复错误：作为 ToolMessage 返回，让模型自己调整。
  • 用户可修复错误：中断并请求人工输入。
  • 意外错误：抛出，供调试使用。

Anthropic 会在工具处理器内部捕获失败，并把错误结果返回给模型，让循环继续跑。Stripe 的生产 harness 会把重试次数限制在两次。

9. 护栏与安全（guardrails and safety）

OpenAI SDK 有三层护栏：输入护栏在第一个 agent 上运行，输出护栏在最终输出上运行，工具护栏在每次工具调用上运行。Tripwire 机制一旦触发，就会立即停止 agent。

Anthropic 在架构上把权限执行和模型推理分开。模型决定想尝试什么，工具系统决定是否允许。Claude Code 会独立控制大约 40 个工具能力，并在三个阶段检查：项目加载时建立信任、每次工具调用前检查权限、高风险操作要求用户明确确认。

10. 验证回路（verification loops）

这是玩具 demo 和生产级 agent 的分界线。

Anthropic 推荐三种验证方式：基于规则的反馈，比如测试、lint、类型检查；视觉反馈，比如 UI 任务用 Playwright 截图；LLM-as-judge，用另一个子 agent 评估输出。

Claude Code 的创建者 Boris Cherny 提到过，给模型验证自己工作的方式，质量可以提升 2 到 3 倍。

11. 子智能体编排(subagent orchestration）

Claude Code 支持三种执行模型：

  • Fork：父上下文的字节级拷贝。
  • Teammate：独立终端窗格，通过文件邮箱通信。
  • Worktree：每个 agent 拥有自己的 git worktree 和隔离分支。

OpenAI SDK 支持 agents-as-tools 和 handoffs。前者让专家 agent 处理边界清晰的子任务，后者让专家 agent 接管完整控制权。LangGraph 则把子 agent 实现为嵌套状态图。

循环如何运行

现在把这些组件串起来，看一个循环周期里发生了什么。

第一步，prompt assembly。Harness 构造完整输入：系统提示、工具 schema、记忆文件、对话历史、当前用户消息。重要上下文会放在 prompt 开头和结尾，避开 Lost in the Middle 问题。

第二步，LLM inference。组装好的 prompt 被发给模型 API，模型生成输出 token：可能是文本，可能是工具调用请求，也可能两者都有。

第三步，output classification。如果模型只生成文本，没有工具调用，循环结束。如果请求了工具调用，就进入执行阶段。如果请求 handoff，则更新当前 agent 并重启循环。

第四步，tool execution。每个工具调用都会被校验参数、检查权限、在沙箱中执行，并捕获结果。只读操作可以并发执行，写操作串行执行。

第五步，result packaging。工具结果被格式化成 LLM 可读的消息。错误会被捕获并作为错误结果返回，让模型有机会自我修正。

第六步，context update。结果被追加到对话历史。如果接近上下文窗口上限，harness 会触发压缩。

第七步，loop。回到第一步，继续循环，直到满足终止条件。

终止条件通常是分层的：模型输出没有工具调用、超过最大轮次、token 预算耗尽、护栏触发、用户中断，或者安全拒绝。一个简单问题可能只需要 1 到 2 轮。复杂重构任务可能会跨几十次工具调用。

对于跨越多个上下文窗口的长任务，Anthropic 使用过一种两阶段 Ralph Loop：Initializer Agent 先设置环境，包括 init script、progress file、feature list 和初始 git commit；后续每个 Coding Agent 会读取 git logs 和 progress files 来重新定位自己，选择最高优先级的未完成 feature，完成工作后提交，并写下摘要。文件系统负责在上下文窗口之间提供连续性。

真实范例：如何实现这种模式

Anthropic 的 Claude Agent SDK 通过一个 query() 函数暴露 harness。这个函数创建 agentic loop，并返回一个异步迭代器来流式传递消息。运行时是“笨循环”，智能都在模型里。Claude Code 使用 Gather-Act-Verify：收集上下文，采取行动，验证结果，然后重复。

OpenAI Agents SDK 通过 Runner class 实现 harness，有 async、sync 和 streamed 三种模式。SDK 是 code-first，工作流逻辑写在原生 Python 中，而不是图 DSL。Codex harness 又扩展成三层架构：Codex Core、App Server 和客户端表面。CLI、VS Code、Web app 等表面共享同一个 harness，这也是为什么 Codex 模型在 Codex 表面上比在普通聊天窗口里更像“同一个产品”。

LangGraph 把 harness 建模为显式状态图。两个节点 llm_call 和 tool_node，通过条件边连接：如果存在工具调用，就路由到 tool_node；如果没有，就路由到 END。LangGraph 从 LangChain 的 AgentExecutor 演化而来，后者在 v0.2 被弃用，原因是难扩展，也缺少多 agent 支持。LangChain 的 Deep Agents 明确使用 agent harness 这个词，包含内置工具、planning、文件系统上下文管理、子 agent 派生和持久记忆。

CrewAI 使用基于角色的多 agent 架构：Agent 是包裹 LLM 的 harness，由 role、goal、backstory 和 tools 定义；Task 是工作单元；Crew 是 agent 集合。CrewAI 的 Flows 层增加了“确定性骨架”：由硬编码逻辑管理路由和校验，让 Crews 处理自主协作部分。

AutoGen 正在演化为 Microsoft Agent Framework，它较早推动了基于对话的编排。它的三层架构包括 Core、AgentChat 和 Extensions，支持五种编排模式：顺序、并发、群聊、handoff 和 magentic。Magentic 模式中，manager agent 会维护动态任务账本，协调专家。

脚手架隐喻

脚手架不是装饰性比喻，而是很准确的工程描述。建筑脚手架是临时基础设施，让工人能够到达本来够不到的楼层。它本身不建造大楼，但没有它，工人到不了高处。

关键点是：建筑完成后，脚手架会被拆掉。

模型越强，harness 的复杂度就应该越低。Manus 在六个月里重建了五次，每次都删除复杂度。复杂工具定义变成通用 shell 执行，“管理 agent”变成简单的结构化 handoff。

这指向一个共同演化原则：模型现在会在特定 harness 中进行后训练。Claude Code 的模型学会了使用它被训练时的那套 harness。更换工具实现可能会让性能下降，因为模型和外壳之间存在紧耦合。

一个检验 harness 设计是否面向未来的方法是：如果换上更强模型后，性能能提升，而不需要增加 harness 复杂度，那么这个设计是健康的。

定义每个外壳的七个决策

每个 harness 架构师都会面对七个选择。

单 agent 还是多 agent。Anthropic 和 OpenAI 都建议：先尽量把单 agent 做到最好。多 agent 会引入额外开销，包括路由用的 LLM 调用，以及 handoff 过程中的上下文损失。只有当工具超过大约 10 个且明显重叠，或者任务域清楚分离时，才值得拆分。

ReAct 还是 plan-and-execute。ReAct 在每一步交织推理和行动，灵活，但每一步成本更高。Plan-and-execute 把规划和执行分开。LLMCompiler 报告过，相比顺序 ReAct，它能带来 3.6 倍加速。

上下文窗口管理策略。生产中常见五种：按时间清理、对话总结、observation masking、结构化记笔记、子 agent 委派。ACON 研究显示，通过优先保留推理轨迹而不是原始工具输出，可以减少 26% 到 54% token，同时保留 95% 以上准确率。

验证回路设计。计算型验证，比如测试和 lint，提供确定性真值。推断型验证，比如 LLM-as-judge，可以抓住语义问题，但会增加延迟。Martin Fowler 的 Thoughtworks 团队把这分成 guides 和 sensors：前者在行动前引导，后者在行动后观察。

权限与安全架构。宽松模式速度快，但风险高，会自动批准多数动作。严格模式更安全，但速度慢，每个动作都要批准。选择取决于部署环境。

工具作用域策略。工具越多，性能经常越差。Vercel 从 v0 中移除了 80% 的工具，结果更好。Claude Code 通过 lazy loading 实现了 95% 的上下文减少。原则是：当前步骤只暴露最小必要工具集。

Harness 厚度。多少逻辑应该放在 harness 里，多少交给模型。Anthropic 押注薄 harness 和模型进步。图式框架押注显式控制。随着新模型版本能内部处理更多事情，Anthropic 会定期从 Claude Code 的 harness 中删除 planning steps。

Harness 就是产品！

两个产品使用完全相同的模型，也可能因为 harness 设计不同而表现出完全不同的效果。TerminalBench 的证据很清楚：只改 harness，就能让 agent 排名上升 20 多位。

Harness 不是已经解决的通用层。真正困难的工程都在这里：把上下文当作稀缺资源来管理，设计能在错误复合前抓住问题的验证回路，构建能提供连续性且不制造幻觉的记忆系统，并决定要建多少脚手架、要把多少能力留给模型。

这个领域正在走向更薄的 harness，因为模型在变强。但 harness 不会消失。即使是最强的模型，也仍然需要某种东西来管理上下文窗口、执行工具调用、持久化状态，并验证自己的工作。
